Tool contract

A tool has four audiences and they want different things. The runtime validates arguments, code consumes a canonical value, the model reads prose, and a UI renders a card. Collapsing those into one string is what makes tool output either unusable by code or unreadable by the model.

The harness tool definition keeps them separate in one place:

LanguageDefineArguments typed by
TypeScriptdefineHarnessTool from @agentkit/corea Zod schema
Pythondefine_harness_tool from agentkit (also agentkit.runtime.define_tool)a Pydantic model
Goruntime.DefineTool(runtime.ToolSpec[A, V]{...})the struct A (JSON tags, description tags)
Rustruntime::tools::define_tool(ToolSpec::new(...))a serde::Deserialize + schemars::JsonSchema type

It is a different shape from the simpler tool definition the configured level uses (defineTool in TypeScript, define_tool in Python and Rust, agentkit.DefineTool in Go). Both run on the same pipeline.

  • TypeScript
  • Python
  • Go
  • Rust

The arguments are validated (and in Go and Rust, decoded into your type) before execute runs, so the body needs no guard clauses; a call with bad arguments comes back as an error result naming the problem. Without a render, the value is stringified (JSON for anything that is not already a string): fine for simple tools, lossy for everything else.

A tool result has three parts, and each consumer reads the one meant for it:

FieldWho reads it
contentthe model: render(args, value), or the stringified value
valuecode: workflows, Code Mode, your own callers
metathe UI: presentationMeta(args, value), persisted on the tool/result event so a card can be rebuilt on replay

Failures that are values

Section titled “Failures that are values”

A value that describes a failure (a command’s non-zero exit) can still be returned rather than thrown. isError(args, value) marks the result as an error while the model reads the rendered value as usual. The built-in bash tool does this for a non-zero exit, so the session log, UIs, workflows and Code Mode all see the command fail. The same tool shows the card hooks:

Registration

Section titled “Registration”

Registration is effect-scoped: a tool belongs to the plugin that registered it and disappears when that plugin unloads. There is no global tool table to clean up. Registering a name that is already taken in the same registry fails that registration.

A tool that already publishes its own model-facing schema (an MCP server’s tool, for instance) passes it as jsonSchema (json_schema in Python and Rust, JSONSchema in Go) and owns its own validation, rather than having one derived from a placeholder type.

Other definition fields, the same in every language: annotations (readOnlyHint, destructiveHint, … which approval by annotation reads), deferred (keep it out of the request until tool search loads it), timeout (abort the call after this long) and category.

Execution pipeline

Section titled “Execution pipeline”

Every call runs through four extension points, in order:

  1. guard(): a monotonic deny no later listener can undo. Invariants.
  2. tools/pre-execute: the reorderable allow / deny / ask policy layer.
  3. tools/execute: wraps the dispatch itself: deadlines, retries, metrics.
  4. tools/post-execute: transforms the result; tools/result observes it.

Execution never throws. A guard that throws, a policy listener that throws, an approval answerer that throws, and the tool body throwing (in Go and Rust: returning an error or panicking) all become an error result, because a tool failure is a conversation the model can recover from, and an exception out of the pipeline would take the whole turn with it.

Visibility

Section titled “Visibility”

restrict narrows the visible set, and presentation, lookup and execution all read through it, so a hidden tool cannot be called by name either. That is what makes a read-only plan mode real rather than advisory.

Filters are owned by the registry that declares them; guards are inherited from the parent. So a realm can narrow a subagent’s tool set without narrowing anyone else’s, and still cannot escape the parent’s invariants.

Cards

Section titled “Cards”

presentCall and presentResult return a render intent, not markup. A pending call renders as generic, terminal or diff. A completed call adds search and web:

CardCompleted shape
generictitle?, content?
terminaloutput, exitCode?
diffdiffs: { path, oldText, newText }[]
searchshape: "matches" | "paths", results, total?, truncated?
webkind: "search" | "fetch", sources?, summary?

In Python a card is a dict with these keys, in Go a runtime.ToolCallView / runtime.ToolResultView struct with a Card field, and in Rust a ToolCallView / ToolResultView enum with one variant per card. The JSON on the wire is the same in all four.

The tool never imports a UI type; a host maps each card into its own views. @agentkit/react ships a default mapping, and the same cards render in the Vue and Svelte bindings and in the dashboards whichever engine serves them.

Presenters are pure (no I/O, no clock, no session reads) because they run on live streaming and on replay from the meta persisted on the tool/result event. A presenter that throws yields no card rather than crashing the replay.

Go arguments

Go has no frozen maps, so exec.Arguments is a detached copy, and the tool itself always runs on a fresh copy of the original arguments whatever a listener wrote into the map. A tools/execute wrapper that wants to change the arguments passes a new Exec downstream with next(&runtime.ExecuteInput{...}).
