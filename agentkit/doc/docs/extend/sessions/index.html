Session log

Model-visible means logged — one mechanism instead of five features

The session log is an append-only event log, and model history is a projection of it. That is the whole design, and everything else on this page follows from it.

deriveMessages() builds the model's view of the conversation from the log, and it is the only supported way to build it. That single rule is what makes fork, resume, replay, durable UI, and telemetry fall out of one mechanism instead of being five separate features.

The invariant

Anything that reaches a model request must be reconstructable from the log.

If a plugin sneaks context into a request without logging it, the session can no longer be forked, resumed, or replayed faithfully — and the bug does not show up until someone tries. So the rule is enforced at the seam: the loop derives history from the log, and nowhere else.

SessionEvent is a discriminated union, so switch (event.type) narrows event.data with no casts.

Compaction, without mutation

Compaction works the same way: it appends a context/compacted boundary rather than rewriting history. The projection stays a pure function of the log, so the original events are still there for audit, and a fork taken before the boundary still replays the full conversation.

deriveMessages collapses everything up to the boundary into a single summary turn, so the model sees the compacted view while the log keeps the originals.

Fork, resume, replay

Resume is not a feature — it is what happens when a persistent store is mounted and the log is read back. Sequence numbers hydrate from the store on the first append, so a resumed session continues its numbering rather than overwriting history.
