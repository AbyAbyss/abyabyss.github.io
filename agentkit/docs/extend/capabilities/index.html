Capability seams

The kernel and the runtime give you a turn. What makes it a harness is the capability layer on top: the things an agent can actually do, each behind a seam so you can swap the implementation without touching the tools.

Every service here is an ordinary plugin, and agentRuntime() already mounts the services themselves. What you add is a provider (where the work happens) and the tools (what the model sees). Mount what you need, replace what you don’t like.

Execution

Section titled “Execution”
ServiceWhat it ownsReference provider
fsevery file touchthe local machine, or an in-memory filesystem
subprocesswhere a process runsthe local machine, a container, a remote microVM
sandboxargv confinement, applied lastargvSandbox([...])

terminalspersistent interactive sessionslocal terminals, or scripted ones

The shell sitting above the subprocess seam is deliberate. The shell backend owns dialect: bash versus pwsh, which managed variables exist, how a command line becomes argv. The subprocess seam owns where the process runs. Keeping them apart is what lets a Windows composition swap the dialect without touching the sandbox, and a remote composition move execution without touching the dialect.

This program mounts the local machine, the local shell and the bash tool, then runs one command through the ordinary tool pipeline:

  • TypeScript
  • Python
  • Go
  • Rust

A non-zero exit is still a returned value, marked as an error so the session log, UIs and workflows see the command fail (see failures that are values). With enableRunInBackground on and the job tools mounted, the model can also start a command detached and poll it.

To confine commands by the operating system instead, mount the sandboxed shell from the workspace package in place of the local shell. Every command runs in root whatever cwd it asks for, can write only there (plus writableRoots), has no network unless network: true, and the system prompt tells the model so (prompt: false turns that off). It uses the best confinement available (bubblewrap on Linux, sandbox-exec on macOS, a hardened local executor otherwise); pass executor to choose. See Execution seams for the full story.

Persistent terminals

Section titled “Persistent terminals”

A one-shot shell loses everything between calls: a cd, an activated virtualenv, an SSH session, a REPL. That is the right default (reproducible and cheap), which is exactly why the stateful case needs its own seam rather than a flag on the stateless one. Mount the local terminals provider and the terminal tools (terminal_open, terminal_send, terminal_read, terminal_signal, terminal_list, terminal_close).

The local terminals are backed by pipes, not a PTY, in every language. A real terminal needs a native PTY module, and making the runtime need one to get a bash tool is a bad trade. Pipes keep cwd and exported environment, which is the reason to want a persistent session at all. What they do not give you is a TTY: no job control, no line editing, and programs checking isatty() take their non-interactive branch. Mount a PTY-backed provider when a session needs those; the tools do not change.

Background work

Section titled “Background work”

The jobs service is kind-agnostic on purpose. A background shell command, a detached subagent and a long terminal send are the same shape once started (something producing output that a model wants to poll, read and stop), so three tools (job_list, job_output, job_kill) cover producers that did not exist when they were written.

  • TypeScript
  • Python
  • Go
  • Rust

Reads are incremental by default, so polling a chatty job does not re-send its history. exit() is optional: a producer with no exit-code concept simply never calls it, and the record keeps the exit code unset rather than claiming a 0 it did not earn. A settled job reaches the model through the agent’s inject path rather than requiring it to remember to poll.

Commands

Section titled “Commands”

The commands service is for things a person asks the harness to do directly. /compact is a decision the user already made; spending a model request to re-derive it is waste.

  • TypeScript
  • Python
  • Go
  • Rust

Dispatch returns nothing for text it does not own, so the fall-through to the model is explicit. An unknown /name returns an error outcome naming the available commands. A throwing command becomes an error outcome rather than taking down whatever dispatched it.

Asking the user something

Section titled “Asking the user something”

The user-questions service is distinct from tools/ask, which answers one fixed question (“may this tool run?”). This one carries an arbitrary question with its own options, so plan approval, a disambiguation prompt and a credential request are all one mechanism a UI implements once. Mount the ask-user tool to let the model ask, and register a provider that knows how to reach a person:

  • TypeScript
  • Python
  • Go
  • Rust

With no provider mounted it declines rather than blocking. An unattended run must not hang forever on a person who is not there. On the configured level, the same questions reach a browser through the server’s question:* events and the client’s answer().

Task tracking

Section titled “Task tracking”

Mount todos with allowParallelInProgress set. It is required with no default: it changes the tool description the model reads, and a harness should state which working style it wants rather than inherit one.

The list is not projected into model history. It reaches the model as a prompt section rendering current state, so a hundred edits cost one rendering, while the log still holds every todo/write revision for a UI to replay.

Knowledge

Section titled “Knowledge”
ServiceToolsNote
webweb_search, web_fetchthe fetch-web provider covers fetch and reduces HTML to prose; search needs a backend (Tavily when TAVILY_API_KEY is set)
lsplspdefinition, references, hover, diagnostics, symbols
sessionQuerysession_search, session_trace, session_listread-only, over past logs

Grep finds a string; an index finds a symbol. The difference matters most where an agent is weakest: a real call site rather than a comment mentioning it, the type error before the build runs.

Both web and lsp follow one rule: the tools stay registered with no provider mounted and fail with a structured WEB_UNAVAILABLE / LSP_UNAVAILABLE the model can read and route around. A schema that appears and disappears with deployment configuration makes the same session behave differently for reasons the model cannot see, and it defeats prompt caching.

Protecting the context window

Section titled “Protecting the context window”

Mount a spill store (fileSpill with a dir, or the in-memory one in tests) and spillPolicy with maxChars and headChars (max_chars / head_chars in Python and Rust, MaxChars / HeadChars in Go).

A grep matching four thousand lines is not a bug: the answer really is four thousand lines. Truncating throws away what the model needed; inlining costs the window. Spilling keeps the whole result addressable and returns a head plus a locator.

It is a tools/post-execute listener rather than a per-tool feature, deliberately: a tool author should not have to think about the context window, and a policy that only covers the tools that remembered to opt in is not a policy. The canonical value is untouched, so code and Code Mode still get everything. Only what the model reads is capped.

Images

Section titled “Images”

Mount the read-image tool. Bytes stay out of the message stream; the log records that an attachment was added. Execution refuses unless the routed model declares image input through its adapter’s capabilities(model) (for example { imageInput: model.startsWith("claude-") }).

Per-model rather than per-provider, because one provider’s models rarely agree. An adapter that declares nothing is treated as text-only: guessing wrong sends a request that fails on the wire, which is worse than declining locally.

Deterministic work

Section titled “Deterministic work”

A loop lets the model choose the next action; a workflow fixes it in advance. Both are useful, and the mistake is making one pretend to be the other. Register a workflow on the workflows service and mount the workflow tool to let the model start one:

  • TypeScript
  • Python
  • Go
  • Rust

Steps declare needs, so independent ones run concurrently without the author scheduling anything. The graph is validated at registration, not at run time: a cycle or a dangling needs is a mistake in the definition, and it should fail while its author is looking at it. For workflows on the configured level (YAML, expressions, agent.workflow.run()), see Workflows.
