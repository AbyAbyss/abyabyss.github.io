MCP

The Model Context Protocol is how agents talk to tool servers: a filesystem server, GitHub, Slack, Linear, a database, or your own. AgentKit is an MCP client in all four languages, and it can also serve your agent as an MCP server so other clients (Claude Desktop, an IDE, another agent) can call it.

An MCP server’s tools join your own tools, named serverId__toolName (for example github__list_issues), and go through the same approvals, tool search, events and traces. Its resources become read-only sources in the prompt.

Transports

Section titled “Transports”
TransportSettingsUse it for
stdiocommand, args, envA local server run as a subprocess (npx, uvx, a binary)
httpurl, headers, authA remote server over streamable HTTP; headers go with every request
mockmock: { tools, resources }Tests, demos and CI: an in-process server, no subprocess or network

http is the streamable-HTTP transport (JSON-RPC 2.0 over POST {url}); there is no separate streamableHttp value. Servers connect on first use, not at construction, so creating an agent never blocks on a slow server.

Every MCP tool reaches the model as a tool, whatever its name; MCP tools are not gated by default except through the usual approval rules (a write_file tool asks, because of its name). To leave a whole server out of one message, deny its prefix: send(input, { tools: { deny: ["github__*"] } }).

Manage servers at runtime

Section titled “Manage servers at runtime”

agent.mcp lists servers, tools and resources, connects and disconnects servers while the agent runs, and calls a tool directly (outside a model turn). The server’s HTTP routes (GET /mcp, POST /mcp/add) expose the same operations to a UI.

  • TypeScript
  • Python
  • Go
  • Rust

OAuth-protected servers

Section titled “OAuth-protected servers”

An http server that answers 401 starts the MCP authorization flow with no configuration: protected-resource metadata, authorization-server metadata, dynamic client registration, PKCE sign-in on a loopback redirect, and token refresh. Tokens are stored under .agentkit/mcp-auth/, so a server signs in once.

Some servers, GitHub’s among them, do not let clients register themselves. Give those a pre-registered OAuth app:

  • TypeScript
  • Python
  • Go
  • Rust
auth keyPurpose
clientId, clientSecretA pre-registered OAuth app, for servers without dynamic registration
scopesWhat to ask for
redirectUrlOverride the callback URL
store, pathWhere tokens are kept: file under .agentkit/mcp-auth/ (default) or memory
onAuthorizeCalled with the sign-in URL; by default a CLI opens the browser
callbackfalse to skip the loopback listener and finish by hand with agent.mcp.completeAuth(id, code)

Create a GitHub OAuth app at GitHub, Settings, Developer settings, OAuth Apps. Its callback URL is where the sign-in lands:

  • CLI or script (an agent on its own): a loopback port AgentKit opens; register http://127.0.0.1/callback (GitHub accepts any port on a loopback callback).
  • Behind the server (servers added with POST /mcp/add or configured on the agent): the agent server itself, at /mcp/oauth/callback/<server id>, for example http://127.0.0.1:8787/mcp/oauth/callback/github. The server lists as unauthorized with an authorizationUrl; open it, sign in, and the callback finishes the flow. The client secret stays on the server and never comes back in GET /mcp.

No OAuth app? A personal access token works as a header: headers: { Authorization: "Bearer <token>" }.

Expose your agent as an MCP server

Section titled “Expose your agent as an MCP server”

Any MCP client can call your agent: the server speaks streamable HTTP and offers one tool, agent__run, which takes a task and returns the run’s output. GET /health answers {"ok": true}.

  • TypeScript
  • Python
  • Go
  • Rust

It binds 127.0.0.1 by default. Binding another host requires a token, which clients send as Authorization: Bearer <token>.

Rust note

In Rust the exposed server runs on the current Tokio runtime and holds the agent weakly: it stops when the agent is dropped or closed.
