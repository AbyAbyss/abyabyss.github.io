Context and budgets

Every model call is built from the same parts: the system prompt, recent history from memory, the tool definitions, snapshots of sources, and the results of earlier tool calls. Left alone, all of these grow until a call no longer fits the model’s window or costs more than it should. This page covers the settings that keep context small and the limits that stop a run that goes on too long.

ProblemWhat handles itDefault
Long conversations overflow the windowCompaction: older turns become a short summaryOn, at 80% of the budget
Large structured payloads waste tokensAdaptive encoding: TOON, compact JSON or CSV, whichever is smallestauto
Too many tools to send on every callTool search: send the likely tools, let the model search for the restOn above 30 tools or about 10k tokens
One huge tool result fills the windowTool-result handles: the model sees a summary and can expand itOn
A run loops or spends too muchStep limit and run budgets8 model calls, no budget

Compaction

Section titled “Compaction”

Before each model call the agent estimates the prompt’s tokens. Past compactAt of the budget it replaces the oldest turns with a short summary and keeps the recent ones verbatim. context:compacting fires before, with the estimate, and context:compacted after, with tokensSaved and the summary length. The conversation in memory is not rewritten; compaction only changes what one model call is given.

Compaction and long-running agents

Compaction is a per-call view. For coding agents and other long sessions, the plugin kernel has a richer compaction plugin (summaries that survive across turns, pinned facts, tool-result trimming); see Context engineering.

Adaptive encoding

Section titled “Adaptive encoding”

Uniform arrays of objects (rows from a database, records from an MCP resource) cost far fewer tokens as a table than as JSON. The encoder tries TOON (a compact, indentation-based format with a header row), compact JSON and CSV, estimates the tokens of each (about four characters a token), and keeps the smallest. The same encoder is available on its own for your pipelines and benchmarks.

  • Python

All four implementations produce the same text for the same input; a shared fixture set checks it.

Which tools a run sees: tool search

Section titled “Which tools a run sees: tool search”

Sending every tool definition on every model call stops working once an agent has a few MCP servers: five servers can be around 55k tokens before the model reads the message, and models pick the wrong tool more often past 30 to 50 tools. Tool search is on by default and turns itself on when a run has more than 30 tools or about 10k tokens of tool definitions. Below that, nothing changes.

When it is on, each model call gets:

  • The likely tools: the best keyword matches between the task and each tool’s name, argument names and description (6 by default), plus anything in alwaysLoad and any tool the run or session allows by name.
  • A catalogue in the system prompt: one line per MCP server or category, with a count and example names, so the model knows what exists: - github (40): list_issues, create_pull_request, ...
  • A search_tools tool: the model asks for what it needs (“post to slack”, “github”) and the best matches become callable on its next step, with their full definitions.

Tools found in a session stay loaded for the rest of it. A tool the model calls by its exact name still runs, even if it was not offered. Tool search works with every provider, because the search runs in AgentKit, not in a provider API.

  • TypeScript
  • Python
  • Go
  • Rust

On a live run with 80 tools across 8 servers (“Let the team know in #eng that the deploy finished”), Claude Haiku 4.5 and GPT-4.1 mini each searched once, found slack__post_message and called it; input tokens for the turn dropped from 14,357 to 4,598 and from 5,398 to 1,995.

In traces, each llm.stream span records toolsOffered and toolsDeferred, and each search is an ordinary search_tools tool span.

With tool search off (toolSearch: false, or auto below the thresholds), up to context.maxTools MCP tools (default 64) go to the model as they are, and past that they are ranked by keyword match with the task. Tools the run or session allows by name, and every tool of a server connected at runtime (agent.mcp.connect, POST /mcp/add), always stay.

The plugin kernel has the same behaviour as the deferredTools plugin; see Context engineering.

Tool-result handles

Section titled “Tool-result handles”

A tool result longer than compactToolResultsAbove characters is stored in a per-run handle store. The model sees { handle, summary } and can call the built-in expand_tool_result tool to read the full payload when the summary is not enough. Handles live for one run and are not persisted. The helpers are public for custom loops: createToolResultHandleStore, compactToolResult and expandToolResult (snake_case in Python and Rust; in Go, in the contextengine package).

Step limits and run budgets

Section titled “Step limits and run budgets”

The reasoning loop stops after 8 model calls in one run (subagents set their own maxSteps, see Orchestration). A budget caps what a run may spend: tokens, estimated cost, tool calls and wall-clock time. Set an agent-wide budget in the config, or pass one per run to override it. When a limit is crossed the run stops at the next check (between steps and tool calls) with a budget error that says which limit and the usage so far.

  • Python

Transient provider failures (network errors, 429s, 5xx) are retried with exponential backoff before any output is streamed, so a retry never duplicates tokens; retry in the config tunes it (maxRetries, initialDelayMs, maxDelayMs).
