Session log

The session log is an append-only event log, and model history is a projection of it. That is the whole design, and everything else on this page follows from it.

  • TypeScript
  • Python
  • Go
  • Rust

Deriving messages builds the model’s view of the conversation from the log, and it is the only supported way to build it. That single rule is what makes fork, resume, replay, durable UI and telemetry fall out of one mechanism instead of being five separate features.

Every event carries seq (monotonic within the session), sessionId, time, type and data. Rust names the type field kind, because type is a keyword; it serializes as type.

The invariant

Section titled “The invariant”

Anything that reaches a model request must be reconstructable from the log.

If a plugin sneaks context into a request without logging it, the session can no longer be forked, resumed or replayed faithfully, and the bug does not show up until someone tries. So the rule is enforced at the seam: the loop derives history from the log, and nowhere else. Even context a tool pushes in with exec.inject(...) lands as a context/injected event first.

Adding a durable fact

Section titled “Adding a durable fact”

A plugin that needs durable state appends its own event type and, if the model should see it, registers a projector that says how. Register no projector and the fact is still durable, still visible to the UI and to telemetry, and simply stays out of the prompt. That is the normal case for metrics and UI state.

  • TypeScript
  • Python
  • Go
  • Rust

SessionEvent is a discriminated union, so switch (event.type) narrows event.data with no casts.

A Go projector returns the (possibly extended) slice rather than mutating it in place.

Use a namespaced type (review/verdict, myplugin/state) so your events never collide with the runtime’s. The built-in types are turn/start, turn/end, step/start, step/end, user/message, assistant/chunk, assistant/message, tool/call, tool/result, context/injected, context/compacted and error; plugins add their own, such as structured/output, todo/write and budget/exceeded.

Compaction, without mutation

Section titled “Compaction, without mutation”

Compaction works the same way: it appends a context/compacted boundary rather than rewriting history. The projection stays a pure function of the log, so the original events are still there for audit, and a fork taken before the boundary still replays the full conversation.

  • TypeScript
  • Python
  • Go
  • Rust

Deriving collapses everything up to the boundary into a single summary turn, so the model sees the compacted view while the log keeps the originals. You rarely write the boundary yourself: the compaction plugin asks a model for the summary and appends it when a session grows too long or a request overflows.

Fork, resume, replay

Section titled “Fork, resume, replay”

Fork is the copy shown at the top of the page: the whole log, or the log through a sequence number, into a new session id. “Retry from here” and “branch this conversation” are the same operation.

Resume is not a feature: it is what happens when a persistent store is mounted and the log is read back. Sequence numbers hydrate from the store on the first append, so a resumed session continues its numbering rather than overwriting history. Replay is reading the events in order; the UI’s assistant/chunk deltas are logged so a replay reproduces the original stream.

Watching the log

Section titled “Watching the log”

session/event is emitted for every append. A UI, a telemetry exporter and a persistence layer are all the same kind of subscriber:

  • TypeScript
  • Python
  • Go
  • Rust

This is why the transcript UI in mini-harness imports no tool, and gets new tools’ cards for free. On the configured level, the same stream reaches a browser or another process through the server, which serves the log with reconnect-safe streaming.

Swapping the store

Section titled “Swapping the store”

A store is four methods: append, read, list and drop. The in-memory store is the default; the sessionPersistence plugin swaps in SQLite or JSONL (see Agent runtime: persistence), and { kind: "custom", store } takes your own.

LanguageStore interfaceBuilt-in stores
TypeScriptSessionStoreMemorySessionStore; SQLite and JSONL through sessionPersistence
Pythonagentkit.runtime.SessionStore (a protocol; methods may be sync or async)MemorySessionStore; SqliteSessionStore, JsonlSessionStore in agentkit.harness
Goruntime.SessionStore interfaceruntime.MemorySessionStore; SQLite and JSONL stores in harness
Rustruntime::types::SessionStore traitMemorySessionStore; SQLite (feature sqlite) and JSONL stores in agentkit::harness

useStore is scoped like any other registration, so unloading the persistence plugin puts the in-memory store back rather than leaving the runtime pointed at a closed handle.

Tip

The JSONL line format is shared by all four engines, so a session recorded by a TypeScript server can be resumed or inspected by a Go, Python or Rust process, and the other way round.
