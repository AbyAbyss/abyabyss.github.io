Context engineering

Deferred tools, approval by annotation, compaction, spill, dynamic subagents, and what the loop does on its own

Everything the model sees on a step is context: the system prompt, the tool schemas, the history, the tool results. Too little and the agent guesses; too much and reasoning degrades while cost climbs. The runtime ships a set of plugins that keep that balance, each an ordinary plugin on the public extension points, each removable.

Several of these follow the design of TrueForge (MIT), an open-source agent harness whose context-engineering layer we read closely: deferred tool loading, the compaction prompt, large-result offloading, annotation-based approvals, and model-authored subagents. Where AgentKit's behaviour differs on purpose, this page says so. The grand tour exercises every plugin here in a runnable example.

Tool annotations and selectors

A tool can say what it does to the world:

annotationmeaning
readOnlyReads only; changes nothing the caller can observe.
destructiveMay delete or irreversibly change something.
idempotentCalling it twice with the same arguments equals calling it once.
delegatesRuns other tools through the pipeline; policy applies to those, not to this wrapper.

Policies take lists of selectors: literal names or the tags @all, @read-only, @write, @destructive.

One deliberate difference from TrueForge: there, an unannotated tool matches no tag but @all. Here an unannotated tool matches @write. Most tools in a codebase say nothing about themselves, and a policy of "ask before writes" that silently skipped all of them would not be a policy. Declare readOnly to opt a tool out.

Deferred tool loading

A deferred tool stays registered and callable, so ctx.tools.execute and Code Mode still reach it. What changes is ctx.tools.schemas(): the model's request carries only the non-deferred schemas plus three meta-tools.

meta-toolpurpose
list_toolsNames and short descriptions of the deferred tools, optionally by category.
get_tool_infoOne tool's description, input schema, category and annotations.
call_toolRun a deferred tool by name. The inner call goes through the full pipeline, so guards, tools/pre-execute, hooks, metrics and the session log see it as they would a direct call.

A prompt section lists the catalogue, grouped by category, so the model knows what exists. ctx.tools.defer(predicate) is the registry primitive underneath; a realm inherits its parent's deferrals and cannot undo them.

Approval policy

allow wins over requireApproval. deny is registered as a guard, so no later tools/pre-execute listener, however permissive, can lift it. A tool with delegates: true (call_tool, create_subagent) is passed through: the calls it makes are gated one by one. Questions go out on tools/ask; with no responder mounted, the call is declined.

Compaction

Before each step the plugin reads the last request's input tokens (the provider's own count, from step/end). Past the trigger it asks the model for a structured brief (intent, decisions, files and snippets, errors and fixes, pending tasks, current work, next step) and appends it to the log as context/compacted. The projection then collapses everything before that boundary into the brief plus a continuation instruction. Nothing is deleted; a resumed session sees what the model saw.

The same path handles a provider's "context window exceeded" error: compact, then let the loop retry. compaction/done reports what happened.

The trigger derivation (a ratio of the context window, or a fixed count) and the shape of the summary prompt follow TrueForge's compaction capability.

Large results

spillPolicy already capped any single result. It now also:

  • shows the head and the tail of a spilled result, so the model sees the shape of the end as well as the start;
  • truncates an error message instead of spilling it, because an error is for the model to read now, not fetch later;
  • applies a per-step budget (maxStepChars): several results that each fit can still flood a request together, and once a step's inline total passes the budget, later results in that step are spilled too.

TrueForge offloads the largest results first once a step's total is over budget. AgentKit's tool calls run sequentially by default and each result is capped as it arrives, so the budget spills the later results instead; with parallelToolCalls the effect is the same.

Dynamic subagents

create_subagent takes a name, a self-contained task, and (when a model set is configured) which model to use. The child gets a fixed identity, the parent's tools, none of the parent's conversation, and returns only its final answer. Delegation is one level deep unless allowNesting is set. Several create_subagent calls in one step run concurrently when the parent was created with parallelToolCalls: true.

Predefined subagents (ctx.subagents.define plus subagentTool) remain the right choice when the delegate's identity and tool set are a design decision rather than something the model should improvise.

What the loop does on its own

Open tool calls. A turn that dies after logging a tool/call but before its tool/result leaves the model's last message with unanswered calls, which every provider rejects on the next request. At the start of each turn the loop appends a failed tool/result for each such call, telling the model to retry if still needed. It is logged rather than synthesised at projection time: model-visible means logged.

Parallel tool calls. agents.create({ parallelToolCalls: true }) runs one step's calls concurrently. Every tool/call is logged first, then all results in call order once every call has settled, so the log stays deterministic. The default stays sequential.

Not ported, and why

  • Durable approvals. TrueForge ends the turn when a tool needs approval and resumes on a later request that carries the decision. AgentKit's tools/ask waits in-flight. A durable version needs a logged tool/approval-required fact and a resume path in the loop; it is the right next step and is scoped separately.
  • Sandbox-as-a-tool with an in-sandbox MCP bridge. AgentKit keeps the sandbox behind the fs and subprocess seams and runs Code Mode against a CodeRuntime. Bridging tool calls from inside a remote sandbox back to the harness over a transport is a different design, not a port.
  • Token-usage breakdown (harness vs instructions vs tools vs messages) is a good diagnostic; it needs per-section token estimates from the prompt service and is left for a follow-up.
