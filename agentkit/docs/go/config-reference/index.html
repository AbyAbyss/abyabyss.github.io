Config in Go

How createAgent's config, options and results map to the Go port

Config in Go

The Go port takes the same configuration as TypeScript, as a typed struct instead of an object literal. What changes is the host language around it: names, optional values, schemas, functions and errors. This page lists each mapping and why it is that way.

The config is a struct named after TypeScript's keys

agentkit.CreateAgent(config) takes an agentkit.Config (an alias of agent.Config). Each field is the TypeScript key with its first letter capitalised, and nested blocks are their own structs:

TypeScriptGo
provider: "anthropic"Provider: agentkit.Provider("anthropic")
provider: { default, userConfigurable }Provider: providers.ProviderConfig{Default: ..., UserConfigurable: true}
system: "..." or a functionSystem: agentkit.SystemText("...") or agent.SystemFunc(fn)
memory: falseMemory: &memory.MemoryConfig{Disabled: true}
mcp: falseMCP: &agent.MCPConfig{Disabled: true}
thinking: falseNoThinking: true
workspace: { project: false }Workspace: &agent.WorkspaceConfig{NoProject: true}
__test: { mockScript }Test: &agent.TestConfig{MockScript: ...}
  • Optional values are pointers where zero is a meaningful setting: CompactAt *float64, Enabled *bool, AutoApproveAfterMs *int. A nil pointer means "not set, use the default", so 0 and false stay expressible. Blocks are pointers too; a nil block is TypeScript's omitted key.
  • x: false has a name. Go cannot hold false in a struct field, so a block that TypeScript switches off with false has a Disabled field (Memory, MCP, scratch, artifacts) or a No... field (NoThinking, NoProject, NoArtifacts).
  • Validation happens in CreateAgent, with Zod's wording. A bad config returns an error whose message starts Invalid createAgent config: and lists each problem on its TypeScript path (telemetry.sample: Number must be less than or equal to 1); no agent is built.
  • Presets (agentkit.CreateUIPreset, CreateCLIPreset, CreateBackendPreset) return an agent.Config; pass overrides as functions: agentkit.CreateBackendPreset(func(c *agentkit.Config) { c.Mode = agentkit.ModePlan }). The coding preset is workspace.CreateCodingAgentPreset, which returns (agent.Config, error).

TypeScriptGo

await agent.run(task, { output, onApproval })a.Run(ctx, task, agentkit.RunOptions{Output: ..., OnApproval: fn})
agent.stream(task)a.Stream(ctx, task)
agent.session({ userId, meta })a.Session(agentkit.SessionOptions{UserID: "u1", Meta: ...})
agent.setMode("plan")a.SetMode(agentkit.ModePlan)
agent.models.setDefault(id)a.Models().SetDefault(id)
agent.rag, agent.mcp, agent.workflowsa.RAG(), a.MCP(), a.Workflows()

RunResult has Output, Usage, Trace, Cost, StepCount, ToolCalls, Artifacts, Handoff and TraceID, with the TypeScript JSON keys as struct tags.

What is sent, stored or emitted keeps TypeScript's keys

Event payloads, wire bodies, recordings, session logs and anything persisted keep TypeScript's shape. In process, events are typed: types.EventKey[P] pairs an event name with its payload struct, so the compiler checks both sides:

Their JSON tags carry the TypeScript keys, which is what lets a TypeScript UI read a Go server and a recording made by one engine replay in another. Over the wire, the Go client hands payloads to handlers as decoded JSON (map[string]any).

Schemas are Go types

Where TypeScript takes a Zod schema, Go takes a type parameter. A tool's arguments are a struct; its JSON Schema is reflected from the fields and their tags (json, description, enum, default), and the model's arguments are validated with Zod's wording before Execute sees them:

Execute receives the decoded struct. A structured Output comes back as a value of the type you named.

Functions are Go functions, and take a context

Every function-valued key takes a Go function whose first parameter is a context.Context and whose last result is an error:

KeyGo
systemagent.SystemFunc(func(ctx context.Context, pc agent.PromptContext) (string, error)); pc has UserID, OrgID, Meta, Mode, Task
hooks.beforeModel, beforeTool, afterTool, onOutputfields of agent.AgentHooks; each returns a result struct (&agent.BeforeToolResult{Block: "why"}) or nil for no change
approvals.policyfunc(ctx, tool approvals.PolicyTool, session approvals.PolicySessionContext) (approvals.ToolPolicy, error); return "" to fall through
onApproval, onElicitation (run or send options)RunOptions.OnApproval, RunOptions.OnElicitation

Errors, cancellation and closing

  • Errors are returned, not thrown. Where TypeScript throws, Go returns an error. A panic in a tool or an event listener is recovered where TypeScript would catch the throw: the tool's panic becomes a tool error the model reads, the listener's an error event.
  • Cancellation is the context. Cancel the ctx passed to Run or Send where TypeScript passes an AbortSignal; a tool's Execute gets a context that ends with the run or the tool's timeout.
  • Always a.Close(ctx), which disconnects MCP servers and closes memory and cache stores. A client session has Close(), which returns at once (safe inside an event handler), and Shutdown(ctx), which also waits for the event stream's goroutine.
  • Everything is safe for concurrent use: one agent serves many sessions from many goroutines.

Where the port differs, and why

  • Map keys print sorted. Go maps have no insertion order, so a JSON object built from a map[string]any (a tool's schema properties, a stringified result) lists its keys sorted. Use a struct, or a json.RawMessage, where key order matters.
  • JavaScript semantics where they show. String lengths in UTF-16 units, JavaScript's trim() and \s, Number#toString, toFixed and Math.round are reproduced wherever their result reaches the wire, a prompt or a fixture, so output matches byte for byte.
  • Session ownership without AsyncLocalStorage. A session emits through an owned view of the agent's event bus, and each turn carries it in its context, so the server routes subagent, RAG and MCP tool events to the session that raised them. A component that emits on its own should read the bus with events.BusFrom(ctx, fallback).
  • Heavy drivers are opt-in imports, as listed in Getting started.
  • The server is net/http. See One wire, four engines.

Feature status

All of @agentkit/core, @agentkit/runtime, @agentkit/kernel, @agentkit/encoding, @agentkit/workspace, @agentkit/server and @agentkit/client (minus browser-only UI stores) are ported. The file-by-file checklist is Appendix A of docs/plans/python-go-sdk-port.md; sdks/go/README.md has the package table and the conventions.
