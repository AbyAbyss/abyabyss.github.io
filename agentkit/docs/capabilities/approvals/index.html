Approvals

Some tool calls should not run until a person says yes: a deploy, a refund, an email to a customer, a DROP TABLE. Approvals pause the run at that call, ask, and continue or skip based on the answer. The model sees a denied call as a tool error and can explain or try something else.

How a gated call plays out

Section titled “How a gated call plays out”
  1. The model asks for a tool call. The agent checks the approval rules for that tool (below).
  2. If the call needs approval, the agent emits approval:request with a requestId, the toolName, its args, and a preview (a readable summary, or the tool’s own reason).
  3. The run waits. Something decides: an onApproval function you passed to the run, a person through session.approve or session.reject, a UI over the wire (POST /approve), or a timeout.
  4. The agent emits approval:resolved with the decision and who made it, then runs the tool or returns a “denied” tool error to the model.

The rules

Section titled “The rules”

Each tool resolves to one of three policies:

PolicyEffect
autoRuns without asking
approveWaits for a decision
denyNever runs; the model gets a tool error

The agent decides in this order, and the first rule that applies wins:

  1. A deny policy, from any source.
  2. The tool’s own needsApproval(args) returning a reason (asks for this call only).
  3. The policy function, when it returns a policy for this tool and session.
  4. policies by tool name, and autoApprove (a list of names that resolve to auto). MCP’s mcp.autoApprove is merged in here.
  5. The defaults: a tool whose category or name contains one of the require words asks. require defaults to write, delete and send.
  6. Otherwise auto.

  • Python
  • Go
  • Rust
KeyPurpose
policiesTool name to auto, approve or deny
autoApproveTool names that never ask (shorthand for auto policies)
requireWords that make a tool ask when its category or name contains them. Default write, delete, send
policyA function of the tool (name, category) and the session (sessionId, userId, orgId, meta) that returns a policy, or nothing to fall through. Use it for role-based rules
autoApproveAfterMsApprove a pending request on its own after this long, reported as by: "timeout". For demos that wait for a person but must not hang. An onApproval function is never timed

Gate single calls

Section titled “Gate single calls”

A tool can ask for some calls only. needsApproval gets the validated arguments and returns a reason to ask, or nothing to run without asking. The reason becomes the request’s preview, which is what a UI shows. It wins over auto policies; only deny overrides it.

  • TypeScript
  • Python
  • Go
  • Rust

The workspace’s run_command tool uses this for network access: with workspace: { allowNetwork: "ask" } commands run offline, and one that sets network: true asks “This command wants internet access” and runs online only if approved.

Decide in code

Section titled “Decide in code”

For scripts, jobs and tests, pass onApproval (and onElicitation for questions) to the run. The function gets the request and returns the decision; nothing waits on a person.

  • TypeScript
  • Python
  • Go
  • Rust

Decide from a UI

Section titled “Decide from a UI”

In an interactive app the decision comes from a person. Subscribe to approval:request on the session, show the request, and call session.approve(requestId) or session.reject(requestId) when they click. The run waits in the meantime. session.stop() rejects the pending approvals of the run in flight and keeps the session.

  • TypeScript
  • Python
  • Go
  • Rust

Over HTTP the same flow runs between a client and the server: the client receives approval:request on its event stream and calls session.approve(requestId), which posts to /approve. The client is the same in every language and works against a server in any language, see Client and the React ApprovalGate in React.

Events

Section titled “Events”
EventPayload
approval:requestrequestId, toolName, args, preview
approval:resolvedrequestId, decision (approved or rejected), by (session, onApproval, timeout, telemetry or none)
elicitation:requestrequestId, the question, and its choices or schema
elicitation:resolvedrequestId, answered

Every settled request emits its resolved event, whoever settled it, so every open UI can clear its prompt.

Questions back to the user

Section titled “Questions back to the user”

Elicitation is the same mechanism for questions instead of yes or no: the agent (or an MCP server, through the MCP elicitation protocol) asks the user something and waits for the answer. Answer with onElicitation in code, or session.answer(requestId, choice) from a UI. Plan mode and todos use it to confirm plans; see Plan mode.

Restrict which tools a session sees

Section titled “Restrict which tools a session sees”

Approvals decide whether a call runs. Tool filters decide whether the model sees a tool at all, per session or per message. A filter has allow and deny lists of names or regexes; a denied tool is never offered to the model.

  • TypeScript
  • Python
  • Go
  • Rust

An approval broker for custom harnesses

Section titled “An approval broker for custom harnesses”

Outside the agent (a plugin-kernel harness, a dashboard, a queue worker), the approval broker parks requests until a person decides. A tool gate calls request and awaits the decision; a UI lists pending() and calls settle. autoApproveAfterMs works here too.
