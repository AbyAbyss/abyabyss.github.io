Agent runtime

Services, the anatomy of a turn, and every extension point

@agentkit/runtime is the agent microkernel: a session log, a tool pipeline, prompt assembly, a model seam, and a loop — each one an ordinary plugin on the kernel.

agentRuntime() is six ctx.plugin() calls. Copy them and swap any one — nothing in it is privileged.

Plus ctx.tools.guard() for a monotonic deny no listener can talk past, and ctx.tools.restrict() for a visible set that presentation, lookup, and execution all read through.

A policy plugin, end to end

A decision is { kind: "allow" }, { kind: "deny", reason }, or { kind: "ask", question }. The runtime — not your plugin — runs the tools/ask serial when a listener answers ask, so asking and answering stay independently replaceable.

The difference between the two mechanisms matters. A tools/pre-execute listener is policy — reorderable, overridable, and the right home for "ask the user". A guard is an invariant — it only ever adds refusals, and a derived registry inherits it, so moving into a realm cannot escape it.

exec carries name, frozen arguments, sessionId, an AbortSignal, and inject(content) for pushing model-visible context into the next request.

Lower order runs first, and the convention leaves gaps: 10 identity, 20 policy, 40 context, 80 skills. The id is stable, so a later plugin can shadow a section by reusing it. ctx.systemPrompt.list() shows what would render, in order.

system-prompt/assemble is the waterfall around the finished prompt, for anyone who needs the last word.

Replacing the loop

Everything else — tools, prompt, log, agents — keeps working, because none of them call the loop; the loop calls them.

Optional plugins

agentRuntime() deliberately mounts only the spine. These ship alongside it and are opt-in, because each one is a policy choice rather than a default:

budget enforces cost, token, tool-call, step, and duration ceilings per session. It is pure bookkeeping over session/event plus two refusals — agent/pre-step for the next step, tools/pre-execute for a call inside a step already underway — so nothing in the loop knows a budget exists. A breach refuses the next step rather than aborting mid-flight, so the log ends on a clean turn boundary.

structuredOutput requires a session's final answer to match a schema:

It adds the requirement to the prompt, validates on agent/turn-stopping, feeds a failed parse back as one more step, and appends the accepted value as a durable structured/output event. A fenced block or surrounding prose is tolerated; anything past the attempt limit is logged as an error rather than looped on.

Subagents are three separate plugins on purpose: subagentsPlugin is the registry, inProcessSubagents is one provider, and subagentTool is the model-facing task tool. Swapping the provider for a forked process or a remote runtime changes nothing else. A definition with tools gets its own realm via ctx.isolate("tools"), so a restricted subagent genuinely cannot reach the parent's other tools, and its identity is a scoped prompt section rather than a user message it could be argued out of.
