Agent runtime

The agent runtime is the agent microkernel: a session log, a tool pipeline, prompt assembly, a model seam and a loop, each one an ordinary plugin on the kernel.

LanguageWhere it lives
TypeScript@agentkit/runtime, re-exported from @agentkit/core
Pythonagentkit.runtime (the common names are also exported from agentkit)
Gogithub.com/AbyAbyss/agentkit/sdks/go/runtime
Rustagentkit::runtime

Mount agentRuntime(), add a model, start, and create an agent on a session. The samples use a scripted model so they run without a key; swap in modelPlugin("anthropic") for a real one:

  • TypeScript
  • Python
  • Go
  • Rust

agentRuntime() is a list of ordinary ctx.plugin() calls, 21 rows in the same order in every language. Copy them and swap any one: nothing in it is privileged.

Services

Section titled “Services”

Each service is reachable from any plugin’s context under the same name in every language (systemPrompt, agentLoop, structuredOutput: Python keeps the camelCase service names too). The way you read one differs:

ServiceTypeScript / PythonGoRust
session logctx.sessionsruntime.Sessions(ctx)runtime::sessions(&ctx)?
tool registryctx.toolsruntime.Tools(ctx)runtime::tools(&ctx)?
prompt assemblyctx.systemPromptruntime.SystemPrompt(ctx)runtime::system_prompt(&ctx)?
model seamctx.llmruntime.LLM(ctx)runtime::llm(&ctx)?
agentsctx.agentsruntime.Agents(ctx)runtime::agents(&ctx)?
loopctx.agentLoopruntime.AgentLoop(ctx)runtime::agent_loop(&ctx)?

In Go and Rust a service method that registers something for its caller takes the caller’s context (runtime.Tools(ctx).Register(ctx, tool), tools(&ctx)?.register(&ctx, tool).await), so the registration unwinds with that plugin. The Rust accessors return an error when the service is not mounted in the context’s realm. They return RuntimeError, while a plugin’s setup returns KernelError, so inside a setup convert with .map_err(BoxError::from)?.

The turn

Section titled “The turn”

Every arrow is a place a plugin can stand. turn/*, step/*, assistant/*, tool/* and user/message are session log events; the names with a slash in the middle of a verb (agent/pre-step, tools/execute) are kernel waterfalls and events.

A policy plugin, end to end

Section titled “A policy plugin, end to end”

This program registers two tools, refuses one with a guard, asks before the other, and answers the question in a separate plugin. It calls the pipeline directly, so no model is involved:

  • TypeScript
  • Python
  • Go
  • Rust

A decision is allow, deny with a reason, or ask with a question:

TypeScript / PythonGoRust
allow{ kind: "allow" }runtime.ToolDecision{Kind: runtime.DecisionAllow}ToolDecision::Allow
deny{ kind: "deny", reason }{Kind: runtime.DecisionDeny, Reason: ...}ToolDecision::Deny { reason }
ask{ kind: "ask", question }{Kind: runtime.DecisionAsk, Question: ...}ToolDecision::Ask { question }

The runtime, not your plugin, runs the tools/ask serial when a listener answers ask, so asking and answering stay independently replaceable. Only a literal true approves; no answer at all declines with Declined: <question>.

The two mechanisms differ in what they promise. A tools/pre-execute listener is policy: reorderable, overridable, and the right home for “ask the user”. A guard is an invariant: it only ever adds refusals, and a derived registry inherits it, so moving into a realm cannot escape it.

The call object (exec) carries the tool name, its frozen arguments, the sessionId, a cancellation handle (an AbortSignal in TypeScript, a CancelSignal in Python, a context.Context in Go, a CancellationToken in Rust), and inject(content) for pushing model-visible context into the next request.

Execution never throws

tools.execute() always returns a result. A guard, a policy listener, an approval answerer or the tool body that throws (or, in Go and Rust, returns an error or panics) becomes an error result the model can read. A policy layer that broke fails closed: Policy failed for "<tool>": <message>.

Prompt assembly

Section titled “Prompt assembly”

Sections are ordered and independently owned, so two plugins can each contribute context without knowing about each other:

  • TypeScript
  • Python
  • Go
  • Rust

Lower order runs first, and a section with no order sits at 50. The convention leaves gaps: 10 identity, 20 policy, 40 context, 80 skills. The id is stable, so a later plugin can shadow a section by reusing it, and disposing the shadow uncovers the original. A section whose render fails is logged and skipped rather than taking the prompt down. list() shows what would render, in order.

system-prompt/assemble is the waterfall around the finished prompt, for anyone who needs the last word. A listener that rewrites the text owns preserving what other plugins contributed.

Replacing the loop

Section titled “Replacing the loop”

The loop is one row. Pass your own plugin that provides agentLoop, or turn the default off and provide one yourself. This loop answers without a model by echoing the user’s message, and it writes to the log the same way the real loop does, so history, replay and persistence keep working:

  • TypeScript
  • Python
  • Go
  • Rust

Everything else (tools, prompt, log, agents) keeps working, because none of them call the loop; the loop calls them. A loop that wants the real step semantics can still reuse the runtime’s helpers: runTurn (TypeScript), run_turn (Python) and their Go and Rust ports drive one turn over the services.

Optional plugins

Section titled “Optional plugins”

agentRuntime() deliberately mounts only the spine. These ship alongside it and are opt-in, because each one is a policy choice rather than a default:

The context engineering plugins (deferredTools, approvalPolicy, compaction, spillPolicy, dynamicSubagents) and todos, hooks and Code Mode are opt-in the same way.

  • TypeScript
  • Python
  • Go
  • Rust

budget enforces cost, token, tool-call, step and duration ceilings per session (maxCostUsd, maxTokens, maxToolCalls, maxSteps, maxDurationMs). It is pure bookkeeping over session/event plus two refusals: agent/pre-step for the next step, and tools/pre-execute for a call inside a step already underway. Nothing in the loop knows a budget exists. A breach refuses the next step rather than aborting mid-flight, so the log ends on a clean turn boundary, and a budget/exceeded event says which limit tripped.

structured output requires a session’s final answer to match a schema: Zod in TypeScript, a Pydantic model (or anything TypeAdapter accepts) in Python, runtime.OutputType[T]() or runtime.OutputJSONSchema(...) in Go, and output_type::<T>() over a schemars::JsonSchema type in Rust. It adds the requirement to the prompt, validates on agent/turn-stopping, feeds a failed parse back as one more step, and appends the accepted value as a durable structured/output event. A fenced block or surrounding prose is tolerated; anything past the attempt limit (two by default) is logged as an error rather than looped on.

Subagents are three separate plugins on purpose: the registry, one provider, and the model-facing task tool. Swapping the provider for a forked process or a remote runtime changes nothing else. A definition with tools gets its own realm via isolate("tools"), so a restricted subagent really cannot reach the parent’s other tools, and its identity is a scoped prompt section rather than a user message it could be argued out of.

Persistence

Section titled “Persistence”

The runtime’s own session store is in memory, so the runtime stays usable anywhere. The durable implementations of the same seam ship as the sessionPersistence plugin:

  • TypeScript
  • Python
  • Go
  • Rust

Persistence is scoped like any other registration: unloading the plugin puts the in-memory store back rather than leaving the runtime pointed at a closed handle. The JSONL format is the same line shape in all four languages, so a session written by one engine can be read by another.
