Configuration

Profiles, layered settings, shell-out hooks, and credentials — retuning a harness without forking it

Everything so far is about what a harness can do. This page is about how somebody else deploys and retunes yours without forking it.

Profiles

Bundles answer "what does this feature mount". A profile answers "what does this deployment boot" — and they are different questions, because the same bundles make a CLI, a server and a one-shot runner depending on what else is stacked and in which order.

Layers apply in one order: each bundle in listed order, then the profile's own patches, then whatever the caller passes. A profile is exactly a bundle whose extends is its bundle list, so there is one set of layering rules to reason about rather than two.

describeProfile() prints the resolved rows, not the declaration — what the layers produced, not what each layer hoped for. Every row it prints is addressable by a patch.

Layered settings

Four layers by convention — defaults (0) → home (10) → project (20+) → flags (30). Project files are searched upward from cwd, applied outermost-first, so a nested package's settings beat the repo root's, the same way .gitignore and tsconfig.json already behave. Anyone editing one of these files is relying on that intuition.

Keys are flat

model.id, not { model: { id } }. Merging nested objects across layers means deciding, per key, whether a layer replaces or extends what is under it — and every codebase that has tried has ended up with both and no way to tell which you are getting. Nested JSON files are flattened on load; arrays stay whole, because a partial array merge has no obvious meaning.

Provenance

This is the question a layered config always has to answer at 2am, which is why explain() exists alongside get(). describe() lists the mounted layers; override() sets a value in a layer of its own, so a runtime change is visibly an override rather than an edit to somebody else's file.

A malformed settings file fails loudly at load. Silently ignoring it would mean a typo'd JSON file makes a policy quietly stop applying — the failure mode worth the least tolerance.

Hooks

A hook is not a plugin: it is a line of config pointing at a script. That is the whole point — "run the formatter after every edit" or "never let it touch .env" should not require writing TypeScript, publishing a package, or restarting anything.

Events: PreToolUse, PostToolUse, UserPromptSubmit, Stop. The hook receives a JSON payload on stdin.

the script doesthe harness does
exits non-zerodeny; stderr becomes the reason the model reads
prints JSON {"decision":"deny","reason":"…"}deny, with that reason
prints JSON {"context":"…"}inject it as model-visible context
prints anything elsetreat it as context
exits zero, prints nothingallow

Non-JSON stdout becoming context rather than an error matters: echo is what people reach for first, and a stray one must not read as a refusal. A Stop hook that denies is asking for another step — that is how a "did you run the tests?" gate keeps the agent working.

Hooks are implemented entirely on the existing waterfalls — a hook is one more tools/pre-execute listener. That was the real test of whether those extension points were general enough.

Credentials

A seam rather than scattered process.env reads, for three reasons: a hosted deployment usually has a vault instead of an environment, a missing key should be one clear failure rather than an adapter-specific one, and a value that never becomes a plain property is much harder to log by accident.

Providers are tried highest-priority first and fall through on a miss, so a keychain sits in front of the environment without either knowing about the other. require() names what it tried, and unresolved() lists everything something asked for and did not get — the first thing to check when a provider mysteriously will not authenticate.

envCredentials maps { scope: "anthropic", key: "apiKey" } to ANTHROPIC_API_KEY.
