Plugin kernel

The plugin kernel is the composition layer under AgentKit. Nothing in it is agent-specific: it is contexts, services, plugin lifecycles and events. You don’t need it to use AgentKit. You need it to extend AgentKit without waiting for a config key.

LanguageWhere it lives
TypeScript@agentkit/kernel, also re-exported from @agentkit/core
Pythonagentkit.kernel
Gogithub.com/AbyAbyss/agentkit/sdks/go/kernel
Rustagentkit::kernel

A runtime is a root context. You mount plugins on it, start it, and stop it when you are done:

  • TypeScript
  • Python
  • Go
  • Rust

Starting means “settled”: every plugin whose dependencies exist has loaded, and the rest are waiting. Mounting a plugin never fails the runtime. A plugin whose setup throws, or whose config does not parse, ends in a failed state and the rest of the tree keeps running.

Services

Section titled “Services”

A service is a value published under a name. Every plugin in the tree can reach it, and a plugin that needs it declares it in inject, so it loads only once the service exists:

  • TypeScript
  • Python
  • Go
  • Rust

How each language reads a service:

LanguageReadTyped by
TypeScriptctx.greeteraugmenting the Services interface
Pythonctx.greeter (or ctx.get("greeter")); None when nothing provides itthe class you published
Gokernel.Get[Greeter](ctx, "greeter") returns (value, ok)the type parameter
Rustctx.get::<Greeter>("greeter") returns Option<Arc<Greeter>>the type parameter

defineService is shorthand for a plugin that calls ctx.provide(name, value) in its setup. Providing the same name twice in one realm fails the second plugin. A provided service is owned by the plugin that provided it: when that plugin unloads, the service is revoked and everything that injected it unloads too.

Reversible effects

Section titled “Reversible effects”

Everything a plugin registers is owned by that plugin and unwinds when it unloads, in reverse order, so a later effect that depends on an earlier one is torn down first. An effect’s return value is its undo:

  • TypeScript
  • Python
  • Go
  • Rust

on, provide and every registry method built on top of effect inherit this, so a plugin author almost never writes cleanup by hand. Unloading a plugin really removes it: no orphaned listeners, no stale services. A setup may also return a teardown for anything it opened outside the context; it runs with the rest.

inject: dependencies across time

Section titled “inject: dependencies across time”

A dependency is a relationship over time, not a startup order. The plugin loads when its dependencies appear, unloads when one disappears, and reloads when it comes back. An optional dependency does not block loading but still triggers a reload when it changes, so “use telemetry if it is mounted” is a declared relationship rather than a nullable lookup scattered through the body.

  • TypeScript
  • Python
  • Go
  • Rust

pending() lists every plugin that has not loaded, what state it is in, and what it is waiting for. It is the first thing to check when a plugin seems inert. There is also an inline form, ctx.inject(["tools"], body), for a block of setup that should follow a dependency without being its own plugin.

Go and Rust: mounting waits for the load attempt

In Go, rt.Plugin(p) blocks until that plugin’s load attempt settles, and in Rust rt.plugin(p).await resolves at the same point. A plugin still waiting on a dependency counts as settled. A setup that starts long-running work should start a goroutine or spawn a task for it. In TypeScript and Python, plugin() returns the fiber at once and you await it (or start()) to wait.

Five dispatch modes

Section titled “Five dispatch modes”

Events are named, and the dispatcher picks how listeners combine:

ModeShapeTypeScriptPythonGoRust
emitfire and forget; a throwing listener is contained and loggedctx.emitctx.emitctx.Emitctx.emit(name, args).await
parallelawait all, aggregate failuresctx.parallelawait ctx.parallel (an ExceptionGroup)ctx.Parallelctx.parallel (KernelError::Aggregate)
serialin order, first non-empty result winsctx.serialawait ctx.serialctx.Serialctx.serial
bailsynchronous short-circuitctx.bailctx.bailctx.Bailctx.bail
waterfallmiddleware chain; each listener receives nextctx.waterfallctx.waterfallkernel.RunWaterfallkernel::run_waterfall

“Empty” means null/undefined in TypeScript, None or False in Python, nil in Go, and None (or false) in Rust.

waterfall is the mode that turns an observation channel into an extension point. A waterfall carries one named input object, so adding a field later never breaks the plugins already listening on it. A listener may refuse (answer without calling next), delegate (next()), or rewrite what everything downstream sees (next(newInput)). The owner runs the chain around its own default behaviour:

  • TypeScript
  • Python
  • Go
  • Rust

Listener order is explicit rather than accidental: listeners run in registration order, and prepend ({ prepend: true } in TypeScript, prepend=True in Python, kernel.ListenerOptions{Prepend: true} in Go, ListenerOptions { prepend: true } in Rust) runs one before those already registered.

Typed waterfalls in Go and Rust

The untyped ctx.Waterfall (Go) and ctx.waterfall (Rust) pass any / AnyValue. Prefer kernel.OnWaterfallOf and kernel.RunWaterfall (Go) or on_waterfall_of and run_waterfall (Rust): they check the input and output types for you and report a mismatch as an error naming the event. The runtime’s own extension points (tools/execute, agent/pre-step, …) are typed this way; their input types live in the runtime package.

Realms

Section titled “Realms”

isolate(name) gives a subtree its own instance of one service. Everything else still comes from the tree above it:

  • TypeScript
  • Python
  • Go
  • Rust

This is how a restricted subagent really cannot reach its parent’s tools, rather than being asked nicely not to. A derived tool registry inherits its parent’s guards (so an invariant cannot be escaped by moving into a realm) while owning its own filters (so narrowing stays local). Two isolates with the same key share one realm (isolate(name, key) in TypeScript and Python).

Services and the caller’s context

Section titled “Services and the caller’s context”

A registration made through a service belongs to the plugin that called the service, not the plugin that provided it. When the caller unloads, its tools, sections and listeners go with it, even though the registry stays:

  • TypeScript
  • Python
  • Go
  • Rust

Because callers see a per-context view, keep mutable service state in fields holding objects (Map, Set, an array, or a shared object). this.items.set(k, v) mutates the shared instance; this.count = 1 would write to one caller’s view and be invisible to everyone else.

Subclass agentkit.kernel.Service to get the per-reader self.ctx. Keep mutable state in attributes that hold objects (dict, set, list); assigning self.count = 1 writes to one caller’s view.

The runtime’s services follow this rule: runtime.Tools(ctx).Register(ctx, tool), runtime.SystemPrompt(ctx).Section(ctx, ...). Guard shared state with a mutex; services are called from many goroutines.

The runtime’s services follow this rule: tools(&ctx)?.register(&ctx, tool).await. Keep shared state behind Arc<Mutex<_>> or atomics; services are Send + Sync.

Plugin config

Section titled “Plugin config”

A plugin may declare how to validate and default its config. The schema runs before setup, and setup receives the parsed value:

  • TypeScript
  • Python
  • Go
  • Rust

Config::new(value) keeps a printable JSON form for describe_bundle; use Config::opaque(value) for something that cannot be printed (a client, a provider). kernel::Config is a plugin’s config and agentkit::Config is the agent’s; import one under another name when you need both.

A config that fails to parse fails that plugin’s fiber and leaves the rest of the tree running: one bad row does not take down the harness.
