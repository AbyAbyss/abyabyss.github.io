Execution seams

The fs and subprocess services are where every file and process touch goes. Nothing else in the tree talks to a disk or spawns anything, which is what makes the execution world swappable in one move. A tool calls fs.readFile(path); it does not know whether that lands on a local disk, a container or an object store. That indirection is the point: a tool written for a laptop runs unmodified against a remote sandbox.

Mounting one of the first three points both seams at that world. To write your own, provide a filesystem and a subprocess provider from a plugin that injects fs and subprocess (ctx.fs.useProvider(myRemoteFs), ctx.subprocess.useProvider(myRemoteSpawner)); every file and shell tool moves with it, with no change to any tool.

Confinement is not a provider

Section titled “Confinement is not a provider”

Path limits and read-only modes are deliberately not part of a provider. They are fs/access listeners. workspaceRoot is one (with readOnly for a read-only mode), and you can write your own rule. The operation is read, write, list, stat, remove or mkdir:

  • TypeScript
  • Python
  • Go
  • Rust

Keeping policy out of the provider means swapping the provider does not silently lose the policy: the two are composed, not fused. And because the check lives at the seam, no tool can forget it. A refused access surfaces as an error from the filesystem call (PermissionError in Python), which a file tool turns into an error result the model reads.

Paths outside the root

Section titled “Paths outside the root”

The workspace-root listener and the local machine’s own file provider both check where a path really lands. Relative paths resolve against root, symlinks are followed (a dangling one included, by hand, so a link to a file that does not exist yet still counts where it points), and the result must be inside root or one of extraRoots. A symlink inside the root that points inside still works; one that points outside is outside. Two options decide the rest, with the same spelling on both plugins:

outsideRootA read or write outside
"deny" (default)is refused, with a reason that names outsideRoot and extraRoots
"ask"asks tools/ask, the same approval seam tool calls use. The responder sees an execution named fs/access with { operation, path } as its arguments. With no responder installed nothing can answer, so it is refused, and a headless agent never hangs
"allow"is permitted. There is no file containment at all then: symlinks, .. and absolute paths all reach outside

Extra roots resolve against the process working directory, as root does, and readOnly covers them too. With both plugins mounted, each checks on its own, so to be asked once give the local machine outsideRoot: "allow" and the workspace root outsideRoot: "ask"; otherwise the provider refuses what the listener approved. The same containment cases run in all four languages from one shared fixture.

File containment is not process isolation

This governs the file tools only. A shell command run through the subprocess provider is not confined by it: cat ../secret in bash reads whatever the process can. Real isolation needs an OS sandbox: the workspace package’s sandboxed shell (bubblewrap, sandbox-exec or a hardened local executor), a Docker or Nebius sandbox, or an argv sandbox as below.

Process confinement

Section titled “Process confinement”

Process confinement is a sandbox provider that rewrites argv after every subprocess/spawn listener has had its say. This program wraps every spawn in firejail --quiet; the scripted subprocess stands in for a real one and shows the rewritten command line it received:

The ordering is the security property. A subprocess/spawn listener can vet or rewrite a command, but the sandbox rewrite happens last, so no plugin can rewrite its way out of it, and swapping the spawner provider does not drop the confinement.

Testing without a disk

Section titled “Testing without a disk”

The in-memory filesystem and the scripted subprocess in the samples above are the reference providers, and they make an entire harness testable with no disk and no processes. The mini-harness in every language does exactly this: its tests swap the execution world for an in-memory one and every file and shell tool follows, with no tool change. That is the proof that the seam is real rather than nominal.
