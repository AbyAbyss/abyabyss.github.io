Capability seams

The services a harness is actually made of — shells, jobs, commands, todos, web, LSP and the rest

The kernel and the runtime give you a turn. What makes it a harness is the capability layer on top: the things an agent can actually do, each behind a seam so you can swap the implementation without touching the tools.

Every service here is an ordinary plugin. Mount what you need, replace what you don't like.

ctx.shell sitting above ctx.subprocess is deliberate. The shell backend owns dialect — bash versus pwsh, which managed variables exist, how a command line becomes argv. ctx.subprocess owns where the process runs. Keeping them apart is what lets a Windows composition swap the dialect without touching the sandbox, and a remote composition move execution without touching the dialect.

Persistent terminals

A one-shot shell loses everything between calls: a cd, an activated virtualenv, an SSH session, a REPL. That is the right default — reproducible and cheap — which is exactly why the stateful case needs its own seam rather than a flag on the stateless one.

nodeTerminals is backed by pipes, not a PTY. A real terminal needs node-pty, a native module, and making the runtime need a compiler to get a bash tool is a bad trade. Pipes keep cwd and exported environment — which is the reason to want a persistent session at all. What they do not give you is a TTY: no job control, no line editing, and programs checking isatty() take their non-interactive branch. Mount a node-pty-backed provider when a session needs those; the tools do not change.

Background work

ctx.jobs is kind-agnostic on purpose. A background shell command, a detached subagent and a long terminal send are the same shape once started — something producing output that a model wants to poll, read, and stop — so three tools cover producers that did not exist when they were written.

Reads are incremental by default, so polling a chatty job does not re-send its history. sink.exit() is optional: a producer with no exit-code concept simply never calls it, and the record keeps exitCode undefined rather than claiming a 0 it did not earn. A settled job reaches the model through agent.inject() rather than requiring it to remember to poll.

Human interaction

Commands

ctx.commands is for things a person asks the harness to do directly. /compact is a decision the user already made; spending a model request to re-derive it is waste.

dispatch returns undefined for anything it does not own, so the fall-through to the model is explicit. A throwing command becomes an error outcome rather than taking down whatever dispatched it.

Asking the user something

ctx.userQuestions is distinct from tools/ask, which answers one fixed question ("may this tool run?"). This carries an arbitrary question with its own options, so plan approval, a disambiguation prompt and a credential request are all one mechanism a UI implements once.

With no provider mounted it declines rather than blocking. An unattended run must not hang forever on a person who is not there.

Task tracking

allowParallelInProgress is required with no default: it changes the tool description the model reads, and a harness should state which working style it wants rather than inherit one.

The list is not projected into model history. It reaches the model as a prompt section rendering current state, so a hundred edits cost one rendering, while the log still holds every revision for a UI to replay.

Grep finds a string; an index finds a symbol. The difference matters most where an agent is weakest — a real call site rather than a comment mentioning it, the type error before the build runs.

Both web and lsp follow one rule: the tools stay registered with no provider mounted and fail with a structured WEB_UNAVAILABLE / LSP_UNAVAILABLE the model can read and route around. A schema that appears and disappears with deployment configuration makes the same session behave differently for reasons the model cannot see — and it defeats prompt caching.

Protecting the context window

A grep matching four thousand lines is not a bug — the answer really is four thousand lines. Truncating throws away what the model needed; inlining costs the window. Spilling keeps the whole result addressable and returns a head plus a locator.

It is a tools/post-execute listener rather than a per-tool feature, deliberately: a tool author should not have to think about the context window, and a policy that only covers the tools that remembered to opt in is not a policy. The canonical value is untouched — code and Code Mode still get everything. Only what the model reads is capped.

Images

Bytes stay out of the message stream; the log records that an attachment was added. Execution refuses unless the routed model declares image input:

Per-model rather than per-provider, because one provider's models rarely agree. An adapter that declares nothing is treated as text-only: guessing wrong sends a request that fails on the wire, which is worse than declining locally.

Deterministic work

A loop lets the model choose the next action; a workflow fixes it in advance. Both are useful, and the mistake is making one pretend to be the other. Steps declare needs, so independent ones run concurrently without the author scheduling anything.

The graph is validated in register(), not at run time — a cycle or a dangling needs is a mistake in the definition, and it should fail while its author is looking at it.
