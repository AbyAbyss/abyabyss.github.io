Dynamic workflows (experimental)

Experimental

The API lives under experimental.dynamicWorkflows and may change between minor versions, in all four languages.

With dynamic workflows on, each session.send(task) becomes: draft a small graph of tool and AI nodes for the task, run the nodes in dependency order, and, when a similar task has come up before, offer to save the graph as a static workflow. The draft comes from the session’s planning model and is validated strictly; when it is unusable a fixed three-node template runs instead.

Use dynamic workflowsUse static workflows
Users describe tasks in chat and you want a visible graph per taskThe pipeline is fixed at deploy time
You want to discover which tasks repeat and turn them into templatesCron jobs and API endpoints with no natural-language input
A React Flow or custom graph UI should render each runHeadless workflows.run(id) is enough

Turn it on

Section titled “Turn it on”

Two settings are required: a workflows config (the store saved graphs go to) and experimental.dynamicWorkflows.enabled. While it is on, a session’s send does not run the normal reasoning loop: it runs the dynamic pipeline and returns the last node’s output.

This agent drafts a graph for each task, prints the graph and each node’s status through a graph plugin, and saves the graph after the second similar task:

Configuration

Section titled “Configuration”
FieldDefaultWhat it does
enabledfalseSwitches a session’s send to the dynamic pipeline
autoPromptSavetrueEmit workflow:save:prompt once a task has repeated enough; false turns the prompt off
repeatAfter2How many similar runs (this one included) trigger the prompt
similarityThreshold0.82Minimum similarity for two tasks to count as the same

Python uses these camelCase keys in its config dict; Go fields are pointers on agent.DynamicWorkflowsConfig (Enabled, RepeatAfter, …) inside agent.ExperimentalConfig; Rust fields are Options on DynamicWorkflowsConfig (repeat_after, …) inside ExperimentalConfig.

Repeat detection

Section titled “Repeat detection”

Similarity is the cosine of the provider’s embeddings when it returns real ones (8 or more dimensions). Providers without an embedding endpoint (Anthropic, the mock) return a placeholder, so the task texts are compared instead: token-set Jaccard overlap, ignoring case, punctuation and common stopwords. “Summarise this week’s support tickets for the product team” and ”… for the engineering team” score about 0.7; an unrelated task scores near 0. That is why the example lowers the threshold to 0.5.

How the graph is drafted and checked

Section titled “How the graph is drafted and checked”

The session’s planning model (provider.routing.planning, else the default model) is asked for JSON of the form { name, nodes: [{ id, type: "tool", tool, args, depends } | { id, type: "ai", prompt, input, depends }] }, given each tool’s description and argument schema. The draft is validated before anything runs:

  • ids are short [A-Za-z0-9_] strings and unique; a graph has 1 to 8 nodes;
  • a tool node that names a tool the agent does not have becomes an AI node;
  • depends keeps known ids and gains every node a {{id.result}} template references;
  • a cycle, a bad id, or an empty or oversized graph rejects the draft.

Any failure falls back to the template graph (the first registered tool, then two AI nodes). The drafting call’s usage is reported on cost:update. AI nodes run without tools and do not stream stream:token; each node’s result is on workflow:step:done.output. With telemetry on, each run is one trace: a workflow.run root (generated: true, workflowId, workflowName) with the node spans under it.

Save a graph as a static workflow

Section titled “Save a graph as a static workflow”

session.saveWorkflow(workflowId, name) (Python save_workflow, Go SaveWorkflow, Rust save_workflow) converts the graph to a static definition (workflowGraphToDef: tool and AI nodes become tool and AI steps) and stores it in the agent’s workflow store. From then on it is an ordinary static workflow: listed by workflows.list(), runnable with workflows.run(id) or session.runWorkflow(id), with approvals in the session. Saved workflows keep the graph’s id.

A UI usually shows the prompt as a “Save this as a workflow?” banner. Over the wire, POST /saveWorkflow (the client’s saveWorkflow) does the same, and the client’s reduceWorkflowRun exposes the pending prompt as savePrompt.

Graph plugins for UIs

Section titled “Graph plugins for UIs”

createGraphPlugin(id, { onGraph, onNodeStatus }) wires two plugin hooks: one receives each drafted graph, the other each node’s status change with the graph as it stands. Use it to drive React Flow, Mermaid or a log, as in the example above (Python create_graph_plugin(id, on_graph=, on_node_status=), Go plugins.CreateGraphPlugin(id, plugins.GraphPluginHandlers{...}), Rust plugins::create_graph_plugin(id, GraphPluginHandlers { .. })).

Limitations

Section titled “Limitations”
  • Small graphs. At most 8 nodes, run one at a time in dependency order.
  • Sessions only. There is no dynamic path for one-shot agent runs; use a session’s send.
  • Two node types. Generated graphs have tool and AI nodes only, no branch or fn steps.
  • Experimental. No semver guarantee on the graph shape or the drafting prompt.
