Config in Rust

How createAgent's config, options and results map to the Rust port

Config in Rust

The Rust port takes the same configuration as TypeScript, as a typed struct instead of an object literal. What changes is the host language around it: names, optional values, schemas, functions and errors. This page lists each mapping and why it is that way.

The config is a struct named after TypeScript's keys

agentkit::create_agent(config) takes an agentkit::Config. Each field is the TypeScript key in snake_case, nested blocks are their own structs (in agent::config or the module they configure), and every optional field is an Option. Config has no Default, because the provider is required: start from Config::new(provider) and use struct update syntax.

TypeScriptRust
provider: "anthropic"Config::new("anthropic") (a ProviderConfigInput from a &str)
provider: { default, userConfigurable }Config::new(ProviderConfig { default, user_configurable: true, .. })
system: "..." or a functionsystem: Some("...".into()) or Some(SystemPrompt::Function(..))
memory: falsememory: Some(MemoryConfig::disabled())
mcp: falsemcp: Some(OrFalse::Disabled)
thinking: falsethinking: Some(Thinking::Off)
handoff: truehandoff: Some(BoolOr::Bool(true))
workspace: { project: false }workspace: Some(WorkspaceConfig { project: Some(OrFalse::Disabled), .. })
__test: { mockScript }test: Some(TestConfig { mock_script: Some(..), .. })
  • None means "not set, use the default", so Some(0) and Some(false) stay expressible: compact_at: Some(0.0), enabled: Some(false). Sub-configs derive Default, so ..XConfig::default() fills the rest.
  • x: false has a type. TypeScript's T | false is OrFalse<T> (Disabled or Set(T)), boolean | T is BoolOr<T> (Bool(b) or Value(T)), and a block switched off as a whole has a constructor (MemoryConfig::disabled()).
  • Validation happens in create_agent, with Zod's wording. A bad config returns AgentError::Config whose message starts Invalid createAgent config: and lists each problem on its TypeScript path (telemetry.sample: Number must be less than or equal to 1); no agent is built. A TypeScript-shaped JSON config deserialises into Config with serde and gets the same checks.
  • Presets (create_ui_preset, create_cli_preset, create_backend_preset) return a Config; override with struct update syntax: Config { mode: Some(AgentMode::Plan), ..create_backend_preset() }. The coding preset is create_coding_agent_preset(CodingAgentPresetOptions::new(root, provider)) (feature workspace), which returns Result<Config, _>.

RunResult has output (a serde_json::Value), usage, trace, cost, step_count, tool_calls, artifacts, handoff, trace_id and status, with the TypeScript JSON keys through serde.

What is sent, stored or emitted keeps TypeScript's keys

Event payloads, wire bodies, recordings, session logs and anything persisted keep TypeScript's shape. In process, events can be typed: an EventKey<P> in agentkit::types::keys pairs an event name with its payload struct, so the compiler checks both sides.

Their serde names carry the TypeScript keys, which is what lets a TypeScript UI read a Rust server and a recording made by one engine replay in another. Over the wire, the Rust client hands payloads to handlers as &serde_json::Value. serde_json is built with preserve_order, so objects keep the key order TypeScript writes.

Schemas are Rust types

Where TypeScript takes a Zod schema, Rust takes a type. A tool's arguments are a struct that derives Deserialize, JsonSchema (schemars) and Clone; its JSON Schema comes from the fields, doc comments become descriptions, and the model's arguments are validated with Zod's wording before the body sees them. Refinements are schemars attributes (#[schemars(length(min = 1))], range, url), checked after the type check and stripped from the schema the model sees. An Option<T> field is optional and accepts null.

The body receives the decoded struct and returns any Serialize value. A structured output (RunOptions.output = Some(output_type::<T>())) is validated against T's schema and comes back as JSON in result.output; decode it with serde_json::from_value::<T>.

Functions are closures that return futures

Every function-valued key is an Arc<dyn Fn(..) -> BoxFuture<'static, Result<..>>>, so a closure returns Box::pin(async move { .. }):

KeyRust
systemSystemPrompt::Function(Arc::new(|pc: PromptContext| Box::pin(async move { Ok(Some(text)) }))); pc has session (user_id, org_id, meta), mode and task
hooks.beforeModel, beforeTool, afterTool, onOutputfields of AgentHooks; each returns Ok(Some(result)) (BeforeToolResult { block: Some(why), .. }) or Ok(None) for no change
approvals.policyArc::new(|tool: PolicyTool, session: PolicySessionContext| Box::pin(async move { Ok(Some(ToolPolicy::Deny)) })); Ok(None) falls through
onApproval, onElicitation (run or send options)RunOptions.on_approval, RunOptions.on_elicitation, which also get the run's CancellationToken

Errors, cancellation and closing

  • Errors are returned, not thrown. Every fallible call returns Result<_, AgentError>. Each variant carries the failing part's error, so a caller can match on it: Config (validation), Loop (LoopError::Budget, an abort, a provider or structured-output failure), Provider, Workflow, Memory, Rag, Mcp, Other (your callback or store) and Message (TypeScript's plain messages, such as Session cancelled). A runtime that fails to build is cached as TypeScript caches the rejected promise: later calls return AgentError::Init around the same error, and err.root() unwraps it.
  • A panic is contained where TypeScript catches a throw. A panic in a tool body becomes a tool error the model reads; one in an event handler is reported on the error event.
  • Cancellation is a CancellationToken (tokio-util). Pass one in RunOptions.cancel where TypeScript passes an AbortSignal; a tool body gets a token that fires with the run or the tool's timeout.
  • Always agent.close().await, which disconnects MCP servers and closes memory and cache stores. A client Session has close(), which returns at once (safe inside an event handler), and shutdown().await, which also waits for the stream's task; dropping the Session closes its stream too.
  • Everything is Send + Sync: an Agent is cheap to clone and one agent serves many sessions from many tasks.

Where the port differs, and why

  • Results are JSON. result.output, tool results and wire payloads are serde_json::Value, because the engine passes them through as TypeScript does; decode them into your types at the edge.
  • define_tool returns Arc<ToolDef> while Config.tools holds ToolDef: unwrap with Arc::unwrap_or_clone.
  • JavaScript semantics where they show. String lengths in UTF-16 units, JavaScript's trim() and \s, Number#toString, toFixed and Math.round are reproduced wherever their result reaches the wire, a prompt or a fixture, so output matches byte for byte.
  • Session ownership without AsyncLocalStorage. A session emits through an owned view of the agent's event bus, carried by each turn in a Tokio task-local, so the server routes subagent, RAG and MCP tool events to the session that raised them. A component that spawns its own task keeps the view with events::spawn_with_bus.
  • mcp::expose holds the agent weakly: the server stops when the agent is dropped (TypeScript and Go keep it alive until close), and it starts only on a running Tokio runtime.
  • Heavy drivers are Cargo features, as listed in Getting started.
  • The server is axum, and the handler has .router() and .close(). See One wire, four engines.
  • Rust-only additions: the tracing sink (feature tracing) and TelemetryConfig.extra_sinks, which runs it next to the collector.

Feature status

All of @agentkit/core, @agentkit/runtime, @agentkit/kernel, @agentkit/encoding, @agentkit/workspace, @agentkit/server and @agentkit/client (minus browser-only UI stores) are ported. The file-by-file checklist is Appendix A of docs/plans/python-go-sdk-port.md; sdks/rust/README.md has the phase table and the development commands.
