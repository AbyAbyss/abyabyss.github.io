Custom UI

AgentKit has no UI of its own that you must use. The server streams events and answers a handful of JSON routes; anything that can read that stream can be the interface. Because the four servers speak the same wire, a custom UI written against one backend runs against the others unchanged.

Pick a level

Section titled “Pick a level”
LevelWhat you writeGood for
Framework bindingsComponents on top of @agentkit/react, @agentkit/vue or @agentkit/svelteMost web apps
@agentkit/client + reducersYour own rendering; the client keeps connection, reconnects and stateOther frameworks (Solid, Angular, Lit), web components, plain HTML
A client in another languageagentkit.client (Python), the Go client package or agentkit::client (Rust), with the same reducersTerminal UIs, desktop apps, bots, backend-to-backend
The raw wirefetch plus EventSource or a WebSocket, or any HTTP libraryMobile apps (Swift, Kotlin), languages without an AgentKit client, third-party AG-UI consumers

Every level sees the same envelope, { type, payload, timestamp }, and the same event names.

Build from reducers

Section titled “Build from reducers”

The reducers are pure functions, (state, event) => state, so a custom UI only has to render their output. createStore(feed, reducer, initial) keeps one in sync with a session:

The Python, Go and Rust clients ship the same session reducers (conversation, pending, plan, todos, usage, workflow) and a session hub that applies them for you; see Client. A terminal UI in any of those languages reads hub.state(id).conversation.messages the same way the browser does.

Design tips

Section titled “Design tips”
  • Events are the source of truth. Do not poll /send or /history for partial text; render stream:token as it arrives and treat done or error as the end of the turn.
  • One stream per UI session. Subscribe as many handlers as you like on one connection. For many chats at once, use one /events/all stream (the session hub) rather than one stream per chat.
  • Subscribe before you send. The server replays nothing. The clients’ send waits for the stream; a raw implementation must wait for the stream to open.
  • Approvals and questions are asynchronous. Show a card on approval:request or elicitation:request and post approve, reject or answer whenever the person decides. Clear the card on approval:resolved or elicitation:resolved, which also fire when someone else settled it.
  • Show nested work separately. Events with a scope come from a workflow step or a subagent. Put them in a side panel or a timeline, not in the main reply.
  • Handle stops and reloads. A stopped turn ends with done and status: "stopped"; keep the partial text. After a reload, fetch history() (or the hub’s seed(id)) before streaming again.
  • Read capabilities. GET /capabilities says whether the agent has workflows, MCP, RAG and a user-configurable model registry, so the UI shows only the controls that work.

Point the UI at a server

Section titled “Point the UI at a server”

Keep the agent URL in configuration, not in code: NEXT_PUBLIC_AGENT_URL, VITE_AGENT_URL or your framework’s equivalent. Changing it from a TypeScript server to a Python, Go or Rust one is the whole migration on the UI side.

Tip

examples/vanilla-js-ui/public/index.html is a complete custom UI in one HTML file: chat, approvals, questions and usage, built on @agentkit/client stores. make vanilla-ui-check runs it in Chromium against all four backends.
