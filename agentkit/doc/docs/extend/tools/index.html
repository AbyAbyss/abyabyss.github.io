Tool contract

One definition, four consumers — arguments, canonical value, model prose, and a UI card

A tool has four audiences and they want different things. The runtime validates arguments, code consumes a canonical value, the model reads prose, and a UI renders a card. Collapsing those into one string is what makes tool output either unusable by code or unreadable by the model.

defineHarnessTool keeps them separate in one definition. (It is exported under that name from @agentkit/core so it does not collide with the simpler defineTool used by createAgent; both run on the same pipeline.)

input is validated before execute runs, so args is typed inside with no guard clauses. Without an output.render the value is stringified — fine for simple tools, lossy for everything else.

Registration

Registration is effect-scoped: a tool belongs to the plugin that registered it and disappears when that plugin unloads. There is no global tool table to clean up.

A tool that already publishes its own model-facing schema — an MCP server, for instance — passes it as jsonSchema and owns its own validation, rather than having one derived from a placeholder Zod type.

Execution pipeline

Every call runs through four extension points, in order:

  1. guard() — a monotonic deny no later listener can undo. Invariants.
  2. tools/pre-execute — the reorderable allow / deny / ask policy layer.
  3. tools/execute — wraps the dispatch itself: deadlines, retries, metrics.
  4. tools/post-execute — transforms the result; tools/result observes it.

Execution never throws. A guard that throws, a policy listener that throws, an approval answerer that throws, and execute itself throwing all become an error ToolResult — because a tool failure is a conversation the model can recover from, and an exception out of the pipeline would take the whole turn with it.

Visibility

Presentation, lookup, and execution all read through the filter, so a hidden tool cannot be called by name either. That is what makes a read-only plan mode real rather than advisory.

Filters are owned by the registry that declares them; guards are inherited from the parent. So a realm can narrow a subagent's tool set without narrowing anyone else's, and still cannot escape the parent's invariants.

Cards

presentCall and presentResult return a render intent, not markup.

A pending call renders as generic, terminal, or diff. A completed call adds search and web:

cardcompleted shape
generictitle?, content?
terminaloutput, exitCode?
diffdiffs: { path, oldText, newText }[]
searchshape: "matches" | "paths", results, total?, truncated?
webkind: "search" | "fetch", sources?, summary?

The tool never imports a UI type; a host maps each card into its own views. @agentkit/react ships a default mapping.

Presenters are pure — no I/O, no clock, no session reads — because they run on live streaming and on replay from meta persisted on the tool/result event. A presenter that throws yields no card rather than crashing the replay.
