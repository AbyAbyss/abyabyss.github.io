Plugin kernel

Contexts, reversible effects, inject, dispatch modes, and realms

@agentkit/kernel is the composition substrate under AgentKit. Nothing in it is agent-specific — it is contexts, services, plugin lifecycles, and events. You do not need it to use AgentKit; you need it to extend AgentKit without asking anyone's permission.

Everything on this page is also re-exported from @agentkit/core.

runtime.start() resolves once the tree has settled — every plugin whose dependencies exist has loaded.

Reversible effects

Everything a plugin registers is owned by that plugin and unwinds when it unloads — in reverse order, so a later effect that depends on an earlier one is torn down first.

ctx.on, ctx.provide, and every registry method built on ctx.effect inherit this, so a plugin author almost never writes cleanup by hand. Unloading a plugin genuinely removes it — no orphaned listeners, no stale services.

inject — dependencies across time

A dependency here is a relationship over time, not a startup-order constraint. The plugin loads when its dependencies appear, unloads when one disappears, and reloads when it comes back.

An optional dependency does not block loading but still triggers a reload when it changes, so "use telemetry if it is mounted" is a first-class relationship rather than a nullable lookup scattered through the body.

runtime.pending() lists what has not loaded and what it is waiting for — the first thing to check when a plugin seems inert.

Five dispatch modes

emitfire and forget; a throwing listener is contained

waterfallmiddleware chain; each listener receives next()

waterfall is the one that turns an observation channel into an extension point. A waterfall carries one named input object, so adding a field later never breaks the plugins already listening on it:

Listener order is explicit rather than accidental — pass { prepend: true } to run before the plugins already registered.

Realms

ctx.isolate(name) gives a subtree its own instance of one service. Everything else still comes from the tree above it.

This is how a restricted subagent genuinely cannot reach its parent's tools, rather than being asked nicely not to. A derived tool registry inherits its parent's guards (so invariants cannot be escaped by moving into a realm) while owning its own filters (so narrowing stays local).

Services and this.ctx

A service is read through the reader's own context, so a registration made inside a service method belongs to the calling plugin:

Because callers see a per-context view, keep mutable service state in fields holding objects (Map, Set, array, or a shared object). this.items.set(k, v) mutates the shared instance; this.count = 1 would write to one caller's view and be invisible to everyone else.
